# HUMANIZED CONTENT STANDARDS & EDITORIAL QUALITY FRAMEWORK

**Document Version:** 2.0 (Phase 12.8 Hardened)  
**Applicability:** All 120 planned technical articles across AIsoftware

---

## 1. CORE PHILOSOPHY: THE EXPERIENCED COLLEAGUE PRINCIPLE

Every article published under the AIsoftware banner must read as though it was authored by an experienced systems architect explaining a non-trivial engineering challenge to a peer.

The goal is **genuine intellectual utility**, not artificial keyword stuffing or algorithmic gaming.

---

## 2. MANDATORY HUMANIZED WRITING RULES

### 1. Problem-Driven Openings
- **Rule:** Begin with an authentic, observable failure scenario or architectural bottleneck that developers face in production.
- **Prohibited:** Generic introductory fluff such as *"In today’s rapidly evolving technological landscape"*, *"Artificial intelligence is revolutionizing the world"*, *"Let's dive in"*, or *"In this article, we will explore"*.
- **Standard:** Open immediately on the technical pain point (e.g., memory exhaustion, split-brain divergence, GPU thread contention).

### 2. Natural Rhythm & Sentence Variation
- **Rule:** Combine short, punchy statements with detailed, explanatory sentences.
- **Avoid:** Formulaic paragraph structures where every paragraph begins with a bullet point or follows a rigid 3-sentence template.
- **Tone:** Technical, direct, educational, and humble. Never arrogant or boastful.

### 3. Absolute Ban on Fabricated Authority
- **Rule:** Never invent personal testing claims, fictional production clients, fake benchmarks, or unverified performance percentages.
- **Hypotheticals:** Clearly identify hypothetical topologies (e.g., *"In a theoretical 5-node cluster..."*).

### 4. Meaningful, Syntactically Valid Code
- **Rule:** All code examples must be valid TypeScript, Python, or SQL.
- **Requirements:** Include typed interfaces, explain key logic blocks, and highlight edge cases (error handling, memory leases, race condition defenses).
- **Prohibited:** Pseudo-code snippets with `// do something here` in critical sections.

### 5. Mandatory "When NOT to Use This" Trade-Off Section
- **Rule:** Every technical guide must explicitly detail scenarios where the featured architecture is inappropriate, overkill, or detrimental.
- **Purpose:** Demonstrates architectural maturity and builds authentic reader trust.

---

## 3. VISUAL ASSET STANDARDS

- **Hero Asset:** Exactly one 1200×630 SVG illustration customized to the title and core architectural mechanism.
- **In-Article Diagrams:** At least two dedicated SVG technical figures (data flows, finite state machines, comparative tables, or sequence diagrams).
- **Accessibility:** All figures must include descriptive captions and `alt` text explaining the diagram's technical significance.
